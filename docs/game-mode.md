# Levik Game 3.0

Game доступен в Windows после подтверждения Game Squad зашифрованным профилем выбранной подписки. Адреса и порты игровых транспортов проверяются по данным профиля, а не по названиям. Игровые серверы исключены из обычного автоматического выбора VPN. Лаунчеры, античит и прочие приложения используют обычные правила VPN; процессные правила относятся только к выбранным игровым `.exe`.

## Выход и вход

Весь игровой IPv4 UDP проходит через один локальный мост независимо от состояния защиты от потерь. Мост работает в отдельном Electron utility process (`dist/main/gameDataPlane.js`) с повышенным приоритетом, чтобы интерфейс, контроллер и сборка мусора main-процесса не задерживали игровые датаграммы. Main получает его состояние раз в 250 мс; прямые измерения D по-прежнему выполняет main, где находятся нативные helper. При падении процесс перезапускается с тем же loopback-портом и UUID (до трёх раз за минуту), текущие потоки открываются заново; если процесс не запускается, мост работает в main-процессе. Мост принимает VLESS UDP и XUDP New/Keep, наблюдает только адреса, порты, время, направления и число пакетов. Содержимое пакетов не анализируется; память процесса игры не читается.

Для первого пакета потока выбирается **выход**. Его публичный адрес и UDP-сокет закреплены до конца потока. Существующий поток не переносится при изменении рекомендаций, предпочтения пользователя, режима защиты или состояния узла. Изменение метаданных узлов применяется на лету. Добавление/удаление транспортов в профиле откладывается до завершения текущих игровых потоков; во время пересоздания соединения новые потоки приостановлены. Отзыв доступа и истечение подписки обрабатываются сразу. `draining` и `disabled` исключены из выбора новых выходов; состояние `draining` позволяет завершить существующие потоки.

**Входы** — транспорты до выхода либо путь через другой игровой узел по межузловому mesh (AEAD или WireGuard). Они могут меняться во время матча, сохраняя экземпляр реле, идентификатор потока и сокет выхода. Между входом и выходом разрешён один переход; петли запрещены. Все пути одного потока должны подтверждать один `instance` выхода. Перезапуск реле выхода меняет `instance`: клиент открывает затронутые потоки заново на этом же выходе, сокет игры сохраняется, но внешний порт выхода меняется.

Если ни один путь к закреплённому выходу не отвечал 1,5 секунды, путь считается молчащим; если так длится 8 секунд, выход считается потерянным, и поток выбирается заново. Для `exitScope=socket` новый выход закрепляется за всем сокетом игры.

Базовые транспорты прогреваются для всех узлов. Дополнительные межузловые ассоциации открываются только к выходам текущих потоков, до трёх других входов, и проходят эхо по всей цепочке перед включением. После завершения потоков эти ассоциации закрываются. Матрица A + M помогает выбрать ещё не открытый путь; график текущего пути использует подтверждённое эхо всей цепочки, без повторного прибавления M.

TCP и IPv6 сохраняют основной игровой маршрут Xray. Начальный TCP-маршрут выбирается по локальной истории выбранной игры, иначе по измерению A. Каталог `shared/games.ts` содержит `exitScope`: `flow` — выбор на поток, `socket` — один выход на игровой сокет, `session` — один выход на время жизни игрового процесса.

При новых реле (capability `eim`) реле открывает один UDP-сокет на игровой сокет клиента и выход: игра видит один внешний IP:port для всех серверов (endpoint-independent mapping), ответы принимаются только от адресов, которым игра писала (до 64). Общие лаунчеры и античит в каталог игровых процессов не входят.

Список процессов проверяется раз в 15 секунд. При обнаружении запуска TCP-выбор повторяется по истории этой игры, пока игровые UDP-потоки ещё не закреплены; иначе текущий выбор сохраняется. При нескольких одновременно запущенных выбранных играх мост не получает достоверной привязки каждого потока к процессу: история записывается как `custom`, а `session` применяется ко всему игровому мосту до остановки игр.

## Измерения и честные подписи

- **A** — UDP-эхо до реле через каждый аутентифицированный транспорт. Пока выбранная игра запущена или наблюдается игровой трафик, проверка идёт раз в секунду, а активные пути потока — 5 раз в секунду; в простое — раз в минуту. Транспорты UDP-поверх-TCP (VLESS) получают штраф 40 мс: потеря в таком потоке задерживает датаграмму до ретрансмиссии.
- **B** — узел → адрес и порт, обнаруженные в трафике игры. Отдельная служба на узле сначала использует ICMP. Для молчащей цели ищется последний отвечающий маршрутизатор пакетами с растущим TTL. Ответ маршрутизатора — нижняя граница, всегда `≈`.
- **D** — непосредственно с физического Windows-адаптера. Существующий C++ helper использует `IcmpSendEcho2Ex` с явным исходным IPv4; перед вызовом Windows API повторно проверяется аппаратный активный интерфейс. При отсутствии ответа используется TTL. До четырёх целей проверяются параллельно, минимум раз в пять секунд, по пять проб с накоплением окна. Если все измеренные цели отвечают быстрее 3 мс, результаты отбрасываются как возможный ответ TUN.
- **M** — измерения соседей по mesh: в AEAD mesh реле само пингует соседей раз в секунду, в WireGuard mesh — служба на узле. Клиент запрашивает строку матрицы через игровой туннель.

Составная оценка равна A + B (+ M для межузлового пути) + примерно 1 мс на каждый узел. Джиттер складывается как корень из суммы квадратов, вероятность доставки — произведением вероятностей доставки участков. Возраст данных и загрузка узла снижают оценку. Все параметры и пороги находятся в `gameEngine.ts`; статистика использует скользящее окно минимум из пяти проверок. Единичная потеря больше не прибавляет прежние 250 мс.

Для неизвестного адреса применяются ступени: измеренная /24 → подтверждённый ключ оператора/маршрута → измеренные регионы сессии → только A. Числовая близость IP не доказывает одного оператора. При отсутствии B интерфейс показывает только A, не выдаёт её за задержку до сервера матча. B запрашивается параллельно на узлах и используется для следующих потоков; теневые проверки показывают альтернативу для следующего матча. Гистерезис выхода — `max(3 мс, 5%)`.

Проверки назначения начинаются с первого подходящего публичного UDP-потока в пределах существующего лимита целей. Для нового адреса без собственного B первые пакеты (до 16) удерживаются примерно на 1,5 × A + 20 мс (40–200 мс), пока узлы возвращают кэшированный B этого сервера; затем выход выбирается и пакеты отправляются. Удержания нет при ручном выборе выхода, `exitScope` не `flow` и при уже измеренном адресе. Для неизвестного региона узлы постоянно измеряют якоря (Valve SDR POP, AWS GameLift beacons), и клиент получает их через `op:"regions"`. Исходная причина выбора сохраняется вместе с потоком. Полные сетевые измерения имеют приоритет над нижними оценками TTL; совпадение адреса цели само по себе не делает ответ промежуточного маршрутизатора полным измерением. Ручное предпочтение остаётся явным выбором пользователя. Следующий выход рассчитывается тем же алгоритмом, что открывает поток, с теми же предпочтениями и историей.

Главная карточка описывает свежий основной UDP-поток матча, а не весь TCP/IPv6-трафик приложения. Одновременные UDP-потоки с разными выходами отмечаются отдельно. Для B показывается состояние конкретного выхода: старое реле, недоступная служба, накопление проб, отсутствие ответа, устаревшие данные или готовый результат. Недоступная служба не маскируется под старую версию протокола и не оставляет прежний B действующим. При известном адресе и пустом графике интерфейс сообщает об отсутствии измерений, а не об ожидании определения сервера.

Главный блок показывает текущий или последний сервер, выбранный выход и причину, сквозную оценку через Levik и D. Схема показывает входы, закреплённый выход и сервер игры. В таблице транспорты сгруппированы по `nodeId`; старые профили группируются по хешу адреса. График относится к составной оценке. Точный игровой ping остаётся в интерфейсе самой игры. Ни ICMP, ни последний маршрутизатор не измеряют внутреннюю обработку игрового сервера.

Проверка 1200-байтного UDP при запуске использует отдельный DNS-пробник как тест доставки данных. Это не измерение A, B, D и не график задержки матча. Пока проверка не пройдена, IPv4 UDP игры заблокирован, обычный VPN продолжает работать. Обход моста при ошибке не включается.

## Защита от потерь

Новая локальная настройка `gameProtection` включена по умолчанию. Старое `gameMultipath: false` не считается отказом пользователя. По умолчанию используются два лучших здоровых пути к выбранному выходу; третий и четвёртый допускаются в пределах 25 мс от лучшего. Резервные ассоциации восстанавливаются без замены сокета выхода. Отключение защиты оставляет тот же мост с одним путём.

Настройка защиты и её фактическая работа показываются отдельно: число доступных путей относится к текущему потоку. Прямой выход может выбираться автоматически и при включённой настройке, но резервных копий через Levik у него нет.

При поддержке реле (`fec`, `spread`) добавляется XOR-parity на группу из 4 пакетов по последнему (резервному) пути и копия с задержкой 2 мс, в обе стороны: один потерянный пакет группы восстанавливается без повтора, а короткий всплеск потерь не задевает обе копии.

При устойчивом росте A на фоне собственной дублированной отдачи число копий временно снижается до одной. Интерфейс называет это предполагаемой очередью отдачи; это эвристика, а не доказанная диагностика провайдера. Через заданный интервал копии проверяются снова. Дополнительный трафик сам по себе не ограничивается.

## Прямой выход, Kill Switch и DNS

Прямой игровой UDP передаётся через отдельный аутентифицированный loopback SOCKS Xray и физически привязанный Freedom outbound, а не через необвязанный UDP-сокет Node.js. Разрешены только публичные IPv4; DNS-порты 53/853 не разрешены. Это использует существующее разрешение для ядра в Kill Switch. Общие правила блокировки и DNS-политика не отключаются.

Нативному helper разрешён только ICMPv4 по его точному executable path; это не разрешение общего UDP/TCP и не исключение для всех приложений. Цель helper должна быть публичным unicast IPv4; исходный адрес должен принадлежать активному аппаратному интерфейсу. Отсутствие D не означает нулевую задержку и не делает прямой путь предпочтительным. При смене сети пересоздаются ядро, ассоциации и измерения; результаты предыдущего поколения отбрасываются.

## Локальная история, установленные игры и согласие

`userData/game-history.json` содержит только игру, /24, необязательный регион, выбранный выход и время. Ограничения: 512 записей и 256 КиБ; запись атомарная. Полные IP, содержимое пакетов, аккаунты и ключи не сохраняются. Этот файл никогда не синхронизируется и не включается в телеметрию.

Обнаружение установленных игр только читает `libraryfolders.vdf`, Steam appmanifest, Epic `.item` и расположение/метаданные Riot. Пути установок не передаются renderer. При запуске выбранного `.exe` подготавливаются измерения; просматривается только список процессов Windows. Запуск лаунчеров и чтение их авторизации не выполняются.

Добавление игр на подключённом VPN использует поддерживаемый закреплённым Xray API `adrules`. Основной маршрут TCP и текущее направление UDP сохраняются при замене правил. Уже открытые ассоциации не меняют свой маршрут. Если API отклоняет обновление, приложение сообщает о переподключении и пересоздаёт туннель. Защита и предпочтение выхода меняются на лету для последующего выбора потоков.

Отдельное, изначально выключенное согласие `gameRegionTelemetry` разрешает агрегат `{v:1,regions:[{region:"RU",matches:1}]}` через существующий HTTPS-клиент телеметрии на `/api/telemetry/v1/game-regions`. Допустимы только коды стран; без IP, cookies, токена аккаунта, installation id и session id. При отсутствии достоверной подписи страны ничего не отправляется. Сервер хранит только день, страну и суммарное число матчей. Согласие на статистику подключений не включает эту настройку.

Отчёт после матча показывает длительность, среднюю/p95 составную оценку, джиттер и доступные счётчики. Если данных последовательностей недостаточно, потери показываются как «Недостаточно данных». Число удалённых дубликатов не выдаётся за число спасённых пакетов. Пропуски до реле по последовательностям ответов не видны.

Отчёт относится к одному завершённому UDP-соединению и сохраняет игру, адрес назначения, выход, причину выбора и фактическое число путей. Он не подписывается как агрегированный отчёт всего матча. Оценки с TTL обозначаются нижней границей; точный игровой RTT остаётся в самой игре.

## Безопасность реле и совместимость

Публичный UDP-слушатель игрового трафика запрещён. Реле — статический Go binary в systemd `DynamicUser` без capabilities, с `ProtectSystem=strict` и лимитами памяти; слушает игровой трафик на `127.0.0.1:37079`. Разрешение Xray ограничено аутентифицированными игровыми инбаундами и точной loopback-целью. В Freedom `finalRules` отдельно разрешают UDP `127.0.0.1/32:37079`, затем блокируют остальное; обычного routing-исключения недостаточно.

Межузловой слушатель в AEAD-режиме открыт nftables только публичным IP пиров; каждый пакет зашифрован AES-256-GCM с ключами из X25519 + HKDF и защищён от повтора. В WireGuard-режиме слушатель доступен только на WireGuard-адресе и известным пирам. Служба измерений — отдельный systemd-процесс с `DynamicUser`, `CAP_NET_RAW`, `NoNewPrivileges`, `ProtectSystem=strict` и Unix-сокетом ограниченного доступа; внешнего сетевого слушателя у неё нет. Реле читает сокет через общую группу `levik-game-ipc`, сохраняя разделение привилегий.

Реле отклоняет частные, зарезервированные, multicast/CGNAT/loopback-цели, адреса игровых узлов и межузловой сети. Пределы Go-реле: 8 путей и 64 потока на сессию, 256 сессий и 4096 потоков глобально, истечение через 60 секунд, бюджеты частоты и объёма. Измерения ограничены 32 целями на сессию, частотой запросов, общим бюджетом зондов и кэшем около 10 минут. Кэш в памяти по /24, без привязки к пользователю.

Протокол LGM2 имеет явную версию и кадры `NODE_INFO`, `PROBE_REQUEST`, `PROBE_RESULT`, `MESH_ROW`, `REGIONS`. Данные (Ping/Pong/Up/Down/Parity) при capability `lgm3` идут компактным заголовком LGM3 в 38 байт; golden vectors общие с Go-реле. Новое реле сохраняет LGM1 для Windows 1.3.46+ и LGM2. Новый клиент со старым реле сохраняет мост, один выход и доступные транспорты; B и межузловые функции не обещаются, интерфейс помечает упрощённый режим. Адреса назначения, содержимое, ключи и пользовательские идентификаторы не пишутся в журналы.

## Проверка и приёмка

Локально: `npm run lint`, `npm test`, `npm run build`. `tests/multipath/goRelay.test.ts` проверяет клиент против собранного Go-реле, если задан `LEVIK_TEST_GO_RELAY` (`make cross-test` в `levik_game_node`). Интеграционные тесты используют настоящий закреплённый Xray, loopback SOCKS и UDP-моки; они не меняют маршруты/DNS компьютера разработчика. На macOS нативные Windows API не исполняются. `scripts/build-kill-switch.ps1` собирает helper в Windows CI, запускает self-test фильтров/валидаторов, проверяет JSON интерфейсов и отказ на loopback-цели, неаппаратном источнике и неверном TTL. CI не запускался через push в рамках этой задачи.

Проверка Windows TUN из существующего workflow использует только тестовый /32, процессы-моки и датаграммы 64/1200/1472 байта, включая UDP/443. Это не проверка реального матча или античита.

Перед включением на серверах оператор запускает dry-run и регламент `levik_game_node/README.md`: реальные UDP-пакеты по каждому транспорту, NODE_INFO, B к публичной цели, отказ для частной цели, отсутствие доступа извне к 37079/Unix-сокету/WireGuard от непиров. UDP-проверки выполнять с EE, поскольку DE control host искажал потери в прежнем исследовании.

Финальная ручная приёмка: CS2 и VALORANT, включая Vanguard; игра выходит через выбранный выход, браузер через обычный VPN; разрыв одного входа сохраняет source IP:port, новый матч выбирает другой выход; Game выключается, просроченный доступ отзывается, смена Wi-Fi/Ethernet пересоздаёт измерения. Нативный D отдельно сверяется с захватом физического интерфейса при активном TUN и Kill Switch. До этих проверок результат не считается проверенным на реальном игровом устройстве.
